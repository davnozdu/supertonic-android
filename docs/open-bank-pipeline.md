# Подготовка записей BigSoundBank · 6 ноября 2026

Скрипт `tools/sound_bank/prepare_bigsoundbank.py` готовит отдельную новую базу.
Действующий сгенерированный банк v11, Android-приложение, телефон и релизы не меняет.

## Запуск и продолжение

Из `/Users/davnozdu/Downloads/supertonic`:

```sh
PYTHONPYCACHEPREFIX=/tmp/mytts-pipeline-pycache python3 supertonic-android/tools/sound_bank/prepare_bigsoundbank.py run --source listening/bigsoundbank-100 --out listening/open-bank --workers 4
```

Предварительно `download_bigsoundbank.py inventory` должен сохранить полный
`inventory.json` и карточки исходников. Обход выполнен: 3483 карточки на 90 страницах,
ошибок нет. Все WAV заранее скачивать не нужно.

Локальные команды (исполняемые файлы уже созданы):

- `listening/open-bank/start.command` — запуск/продолжение всей очереди;
- `listening/open-bank/stop.command` — остановка после текущих файлов;
- `listening/open-bank/status.command` — готово/всего/остаток/ETA/ошибки.

Ctrl+C и SIGTERM также запрашивают корректную остановку. Активны максимум четыре
задания, поэтому остановка не ожидает всю очередь из ста файлов. После перезагрузки
снова выполнить start; автозапуск ОС не устанавливается. Одновременный запуск в одну
папку блокируется файловой блокировкой; после завершения процесса блокировка снимается ОС.

`--batch-size` по умолчанию 100, `--workers` 1–8 (по умолчанию 4), `--limit` позволяет
проверить первые N карточек. Загрузка и обработка идут в тех же рабочих потоках:
не нужно ждать, пока вся сотня докачается, чтобы начать кодирование.

## Три папки

- `events/`: изолированные события и Foley, AAC 128 кбит/с, 44,1 кГц, стерео.
  Длинные записи режутся до 8 с; короткие сохраняют длину, не дополняются тишиной.
- `scenes/`: фоновые звуки сцен; тот же AAC, полная исходная длительность.
- `review/`: неопределённый тип, музыка, речь, технические сигналы, узнаваемые
  рингтоны/джинглы, неясное авторство и другие неоднозначные записи. Для явно не-CC0
  сохраняется карточка, аудио не скачивается. Не включать эту папку в публичные
  базы автоматически. Пользователь может позднее удалить ненужное.

Классификация использует тип и UCS-категорию самой карточки плюс консервативные
исключения. Это автоматическая сортировка по сведениям источника, не прослушивание
и не доказательство семантики каждого звука.

У каждой записи имя `bsb-<исходный номер>-<понятное-английское-название>.m4a`,
например `bsb-0189-car-starting-and-departure.m4a`. Номер обеспечивает стабильность
и различение одинаковых названий. JSON рядом сохраняет исходное описание,
английские теги, русские поисковые слова, автора, URL и лицензию. Автор берётся
из технической карточки: JSON-LD сайта иногда называет владельца сайта вместо
настоящего автора записи (пример: телефон №0253 — DenisChardonnet).

## Выбор восьмисекундного события

Служебное представление: mono 8 кГц, STFT 256 отсчётов, шаг 160. Вычисляются
положительные изменения логарифмического спектра и энергия RMS, оценивается
шумовой фон. Выбирается активное окно и начало события внутри него, оставляется
0,3 с перед началом, если это позволяет файл. Решение/таймкод записываются в JSON.
Анализ спектра не меняет спектр самого итогового аудио.

Растягивания, нормализации, лимитера и других изменений громкости нет. Для сцен
обрезка вообще не применяется. Сомнительное выделение/почти тишина уходит в review.
Отбор по спектру не распознаёт слова или действия и не гарантирует, что любые
два события, разделённые более чем восемью секундами, поместятся в один клип.

## Контроль, удаление и восстановление

После кодирования проверяются AAC/44,1 кГц/stereo, длительность и полное
декодирование без ошибок. Считается SHA256. Сначала атомарно записываются JSON
готового файла и запись `state/<номер>.json`, затем по окончании партии строятся
манифесты и проверенные SQLite-индексы. Только после этого исходники успешно
обработанных файлов удаляются из `--source/audio`. Ошибочные/незавершённые остаются.
Удаление относится к загруженным исходникам этого конвейера, а не ко всем файлам
в папке проекта. Ранее выданные шесть примеров в отдельной папке сохраняются.

При повторном запуске сверяются размер и SHA256 готового результата. Файл с
корректным результатом не скачивается и не обрабатывается повторно. Незавершённые
`.part` не считаются готовыми. Если процесс был оборван между результатом и
обновлением общего индекса, индекс восстанавливается из отдельных state-записей.
После жёсткого отключения питания во время записи потенциально повреждённый
результат будет обнаружен по хешу и обработан заново.

`progress.json` обновляется после каждой записи: total/completed/remaining,
число потоков, размер партии, время, ETA, текущая запись и ошибки. ETA основана
на скорости текущего запуска и меняется в зависимости от длительности сцен.
`errors.json` содержит неудачные задания; они повторяются при следующем запуске.

## Индексы для телефона и публикации

В каждой папке: `manifest.json`, `sounds.db` и аудио с JSON-карточками.
SQLite содержит таблицу sounds и FTS4 `sounds_fts` с unicode61: поиск по названию,
описанию, тегам, категории и русским синонимам; id ведёт к имени файла. FTS4
выбран для совместимости с Android SQLite. Пример поиска:

```sql
SELECT id, title FROM sounds_fts WHERE sounds_fts MATCH 'дверь';
```

Авторство/лицензии также сводятся в общий `CREDITS.md`. Их можно публиковать
отдельно; для CC0 скачивание полного текста лицензии не требуется. Тексты и
карточки источников сохранены в исходном каталоге для учёта.

Это подготовка артефактов; интеграция нового индекса в Android и публикация
ещё не выполнены. Предлагаемая публикация — отдельные версии events и scenes,
пакеты примерно по 100 файлов и общий поисковый индекс, без review. Это позволяет
не создавать тысячи вложений в одном GitHub release и скачивать базу частями.
Для загрузки отдельных клипов из архива потребуется соответствующая поддержка
в Android; текущий SoundBank получает отдельные URL, новая схема не подменяется
его live-манифестом без реализации и проверки.
