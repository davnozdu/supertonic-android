## 1. P1 — конвейер допускает закрытие моделей при работающем producer

**Место:** `ambience/ClipPipeline.kt:50–55`,
`ambience/AmbienceBook.kt:323–334,354`, `ambience/Sa3Generator.kt:265–267`.
Пути указаны относительно `app/src/main/java/com/brahmadeo/supertonic/tts/`.

**Сценарий:** декодер/сохранение падает или работа отменяется, пока producer занят
не отвечающим на interrupt вызовом. `run()` прерывает producer и ждёт максимум
60 секунд. После таймаута не проверяется `isAlive`; прерывание самого `join`
тоже проглатывается. Вызывающий код затем закрывает NPU-сессию и графы либо
переподключает генератор на CPU, хотя producer ещё может их использовать.

**Последствие:** нарушение времени жизни native-ресурсов; возможны падение,
гонка при переключении NPU/CPU или повреждение состояния. Нативное падение на
телефоне в этом аудите не воспроизводилось.

**Проверка:** исполнен настоящий `ClipPipeline` с искусственным producer,
который не отвечает на interrupt. При сбое consume и установленном флаге interrupt
у вызывающего потока `run()` вернулся сразу, пока producer ещё работал.
Отдельная проба без interrupt вызывающего потока вернулась через 60 003 мс,
также при живом producer. Для теста не нужны Android и модели.

**Исправление:** освобождать/переключать графы только после подтверждённого выхода
producer. Если верхнему уровню нужен ограниченный срок отмены, владение ресурсами
должно оставаться у завершающегося worker; новый запуск не должен использовать
тот же генератор. Не проглатывать interrupt без восстановления состояния.

## 2. P2 — быстрый поиск PCM всегда промахивается для русских движков

**Место:** `SupertonicTTS.kt:384–397,420–422,506`.

`generateAudioOne()` ищет ключ `audioKey + output`, а запись результата и второй
поиск используют `audioKey + output + room`. Даже при выключенной акустике
добавляется непустой суффикс `\u0000room=`. Ключи не совпадают.

**Сценарий:** следующий абзац уже находится в PCM-кэше, но фоновый синтез держит
общий монитор модели. Передний план не находит готовый PCM в первом поиске,
ждёт монитор и только внутри него получает правильное попадание в кэш.

**Последствие:** ненужное ожидание инференса будущего текста и паузы при наличии
готового звука. Кэш продолжает работать через второй поиск; утверждать, что он
полностью отключён или что каждый абзац пересчитывается, было бы неверно.

**Проверка:** реальный `SpeechAudioCache` подтверждает промах по первому ключу
и попадание по второму для одной записи без акустики. Несовпадение ключей
установлено непосредственно в обоих местах диспетчера.

**Исправление:** единая функция полного ключа для чтения и записи; учитывать
акустический контекст до ожидания монитора, не меняя состояние сцены дважды.
Проверить случай: ahead занят, нужный PCM готов, передний план сразу получает PCM.

## 3. P2 — Shtorm принудительно добавляет паузы при выключенной настройке

**Место:** `pocket/PocketEngine.kt:45–46,76–81`,
`SupertonicTTS.kt:332–337,369–377`.

Верхний уровень учитывает `tera_punctuation_pauses` и может вернуть нулевую
добавочную паузу. Однако `PocketEngine` всегда передаёт в JNI `sentencePauseMs=180`
и сам доводит тишину в конце пунктуационных кусков до 180 мс. Оба пути обходят
переключатель и выбранное пользователем значение. При слишком коротком хвосте
генерации тишина добавляется даже с выключенным переключателем.

**Последствие:** настройка «паузы выключены» не выполняется, а при длинном тексте
паузы могут появляться и на внутренних границах `PocketText.chunks()`.
Это добавленная тишина, отдельно от естественных пауз самой модели.

**Проверка:** статическая трассировка Kotlin → `NativePocketTts.nativeCreate` →
настройка `sentence_pause_ms` и её использование в `PocketTTS.cpp`.
Звук на телефоне не воспроизводился.

**Исправление:** передавать одну согласованную политику пауз в оба уровня,
учитывать её при пересоздании движка; сохранить добавление только недостающей
тишины. Проверить OFF, 0 мс и пользовательскую длительность, включая длинный текст.

## 4. P2 — после успешного возобновления одна из книг остаётся на паузе без задания

**Место:** `books/prepare/BookQueue.kt:99–109,142–157,198–208,227–233`.

**Сценарий:** на паузе лежат книги A и B. Одно задание `BookResumeJob` запускает A.
При успешном запуске новое задание не назначается: `schedule()` вызывается только
в ветке `!started`. После успешного окончания A `finished()` запускает
`startNext()`, который при `chain=false` пропускает все paused-книги.
Назначения `BookResumeJob` для B в этом пути нет.

**Последствие:** B сама не возобновится. Открытие `BooksActivity` заново назначит
задание, но это уже требует действия пользователя; повторный отказ облака у A
тоже может случайно восстановить расписание.

**Проверка:** статическая трассировка всех вызовов `BookResumeJob.schedule` и
переходов окончания подготовки. Системный JobScheduler на телефоне не проверялся.

**Исправление:** после окончания/удаления/изменения записи пересчитывать ближайшую
paused-книгу и её задание; не оставлять запись A с просроченным `resume_at` целью
нового задания, пока она уже обрабатывается. Нужна проверка двух paused-книг.

## 5. P2 — восстановленная после смерти процесса подготовка не завершает запись очереди

**Место:** `books/prepare/BookQueue.kt:135,145–149`,
`books/prepare/BookPreparationService.kt:46–50`,
`books/prepare/BookPreparation.kt:115–129,267`.

**Сценарий:** Android убивает процесс во время подготовки книги из очереди,
затем сервис получает повторный intent (`START_REDELIVER_INTENT`).
URI/`queue_file` восстанавливается, но `BookQueue.running` — только поле RAM,
оно снова равно null. `execute()` его не восстанавливает.
Когда книга успешно готова, `finished()` выходит на `running ?: return`.

**Последствие:** успешно подготовленная книга остаётся в очереди, последующая
цепочка не запускается. При очередном запуске очереди та же книга выбирается
снова; кэш облака может уменьшить стоимость повтора, но учёт очереди уже неверен.
После ошибки также не обновляется счётчик неудач.

**Проверка:** статическая трассировка redelivery и всех присваиваний `running`.
Принудительная остановка приложения/процесса не выполнялась.

**Исправление:** восстанавливать id записи из проверенного пути внутри book-queue
либо передавать и восстанавливать явный queue id; окончание должно опираться
на идентичность задания, которая переживает смерть процесса.

## 6. P2 — импорт голоса накапливает исходный многоканальный PCM без безопасного бюджета

**Место:** `pocket/PocketCustomVoices.kt:123–169`.

Это установленный по коду риск OOM; падение приложения не провоцировалось.
Двухминутный предел ограничивает длительность, но не расход heap. Весь исходный
PCM накапливается до downmix/resample; далее создаются копия `toByteArray()`,
полный `FloatArray` всех каналов, mono и исправленная копия mono. Частота
проверяется только после накопления, верхнего предела числа каналов нет.

Уточнение после проверки: двухминутный PCM16 stereo 192 кГц содержит 92 160 000
байт PCM, массив float каналов — 184 320 000 байт. В первоначальной оценке
оба размера были ошибочно удвоены. Этот stereo-файл на телефоне успешно
декодировался с heap 512 МиБ. При восьми каналах PCM занимает 368 640 000 байт,
а массив float всех каналов потребовал бы 737 280 000 байт. Восьмиканальный
файл воспроизвёл OOM уже при росте ByteArrayOutputStream: запрошено 536 870 928
байт при лимите heap 536 870 912. `OutOfMemoryError` не перехватывается UI
через `catch(Exception)`. Проверка проведена в отдельном процессе, основное
приложение не падало.

**Последствие:** высокочастотная/многоканальная запись может завершить процесс
вместо понятного отказа импорта. Обычная короткая mono-запись этот сценарий
не обязана вызывать.

**Исправление:** валидировать rate/channels сразу, задать абсолютный бюджет;
downmix и resample выполнять по мере декодирования в ограниченный mono 24 кГц
буфер. Проверять ограничение до добавления очередной порции.
