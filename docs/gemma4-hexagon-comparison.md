# Gemma 4 E2B: второй NPU-пакет и сравнение на CPH2745

6 октября 2026. Телефон OnePlus CPH2745, Android 16, Snapdragon SM8850 / Hexagon V81.
Работа в отдельной ветке `experiment/gemma4-npu`; код и настройки озвучки MyTTS
не менялись. APK `com.davnozdu.gemma4.npuprobe` собирается только на GitHub.

## Выбор пакета

Второй проверенный вариант — [H2Loop E2B Q4_0 / ggml-hexagon](https://huggingface.co/h2loop-ai/gemma-4-e2b-hexagon),
revision `1bb2044c313769541558f2c27fa67561894d0f26`. Это та же Gemma 4 E2B,
другие квантование, формат и runtime. Размер GGUF **2 620 370 976 байт = 2,44 ГиБ**;
SHA256 `e531007218dfab990486a5de7676a6932d6ea8dea233d1f698d7c21cf8a16889`
проверен на компьютере и телефоне перед каждой пробой.

Готовый runtime llama.cpp `0ef6e55` из этого же pinned revision: 13 библиотек,
размеры и SHA256 в `tools/gemma-npu-probe/hexagon-runtime.json`. Они упакованы
в APK вместе с нашим небольшим JNI-мостом. V81 DSP-библиотека загружается через
FastRPC / CDSP; **обычный UID приложения 10487, без root для инференса**.
Драйвер сообщил V81, HMX 1, HVX 8, VTCM 8 МБ. QNN на этом пути не используется.
Root нужен был лишь для предварительных CLI-проб и чтения закрытых файлов диагностики.
Первый запуск из ADB без root не имел доступа FastRPC; это ограничение shell UID,
оно не воспроизводится в обычном Android APK.

Предыдущий пакет RunAnywhere QHexRT E2B V81 действительно работает, но занимает
7,68 ГиБ на диске и существенно медленнее на нашем запросе. 8-bit QNN context
bins H2Loop и E4B не проверялись; автор сам отделяет их статус от Q4. MTP не
скачивался и не включался. Не переносить чужие измерения V79 на этот телефон.

## Одинаковые веса, три устройства

GitHub [37457601321](https://github.com/davnozdu/supertonic-android/actions/runs/37457601321),
commit `d2f0c26a`. Один GGUF и runtime, CPU2, batch/microbatch128, flash attention
on, polling0, отдельно pp128 и tg128, по два повторения. Без промптов проекта,
LLM/TTS-кэша, звука, спекулятивного декодирования и изменения настроек MyTTS.

| Устройство | Вход pp128, ток/с | Генерация tg128, ток/с | Время tg128 |
|---|---:|---:|---:|
| NPU / HTP0 | 1287,4 | **27,80** | **4,60 с** |
| CPU / 2 потока | 64,8 | 17,66 | 7,25 с |
| GPU / llama.cpp OpenCL | 204,9 | 15,27 | 8,38 с |

На этом runtime NPU быстрее CPU **в 1,57 раза** на decode и **в 19,9 раза**
на prefill; быстрее OpenCL GPU в 1,82 / 6,28 раза соответственно. Это короткий
синтетический benchmark, не скорость полного запроса и не долгий thermal soak.
В повторных отдельных NPU-процессах decode 26,83–27,71 ток/с, prefill 1398–1401.
Отдельный GPU-процесс дал 19,32 ток/с decode / 213,62 prefill: выигрыш NPU
на decode здесь 1,39 раза. Кэш/температура/фоновая нагрузка не зафиксированы;
диапазон результатов важнее одного максимального отношения.

## CPU time и RAM в отдельных процессах

Одинаковый native benchmark pp128/tg128 ×2 плюс его штатный warmup и загрузка.
Wall/CPU time всего вызова JNI; не только decode. Память семплируется примерно
раз в 0,5–0,6 с, поэтому краткие пики между выборками не исключены.

| Устройство | Wall вызова | CPU time процесса | Пик PSS | Мин. MemAvailable |
|---|---:|---:|---:|---:|
| CPU2 | 24,947 с | **49,315 с** | 3,53 ГиБ | 4,03 ГиБ |
| NPU | 11,885 с | **11,608 с** | 2,86 ГиБ | 4,43 ГиБ |
| OpenCL GPU | 23,961 с | 14,021 с | 2,66 ГиБ | 3,51 ГиБ |

Таким образом NPU потребовал **на 76,5% меньше суммарного CPU time** и завершил
этот benchmark примерно вдвое быстрее CPU2. Это не процент экономии энергии.
Пики PSS включают Android/JNI/runtime; глобальные DMA-BUF/GPU-счётчики могут
пересекаться с PSS и не складываются с ним. В общем запуске трёх устройств
пик PSS 3,81 ГиБ и минимум MemAvailable 3,38 ГиБ — агрегат, не память одного NPU.

## Сравнение с текущим LiteRT GPU

Отдельный предыдущий APK `c09fb13b`, build37446189662, LiteRT-LM0.17.1:
тот же файл E2B `.litertlm`, что хранит MyTTS, context512, thinking/speculation off.
Одинаковый русский запрос на рассказ, limit128, два запуска с новой conversation.

| Backend/пакет | Повторный рассказ | Токены / wall | CPU time |
|---|---:|---:|---:|
| LiteRT GPU | **3,729 с** | **34,33 ток/с** (128) | 1,258 с |
| QHexRT NPU | 15,408 с | 8,37 ток/с (129) | 10,578 с |

LiteRT GPU **не равен** OpenCL GPU из таблицы выше: runtime, квантование и
шаблоны отличаются. Нельзя объявлять NPU быстрее текущего GPU-провайдера MyTTS
по одному сравнению ggml устройств. LiteRT CPU2 завершился ошибкой
`Failed to allocate tensors`; его скорость не измерена. Это не доказанная OOM
и не отказ всех CPU-вариантов: Q4 CPU2 выше успешно работает.

Пик PSS LiteRT GPU 0,92 ГиБ плюс отдельные GPU allocations; QHexRT 2,19 ГиБ
плюс DMA-BUF. Контекст8192 из рабочего приложения здесь не проверялся.

## Настоящая генерация

GitHub [37458625431](https://github.com/davnozdu/supertonic-android/actions/runs/37458625431),
commit `1c03d417`, отдельный app UID. Тот же запрос на русский рассказ,
контекст512, limit128, thinking off, HTP0. JNI вернулся с exitCode0, записан
успех; модель выдала связный русский текст до лимита. Native CLI сообщает
**25,0 ток/с generation** и **557,4 ток/с prompt**. Wall9,991 с / CPU9,218 с
включают model initialization в новом процессе, local server, warmup и генерацию — их
нельзя напрямую сравнивать с тёплым LiteRT conversation wall из таблицы выше.
Пик PSS2,79 ГиБ; минимум MemAvailable4,89 ГиБ.

Дополнительная проба: GitHub
[37459202051](https://github.com/davnozdu/supertonic-android/actions/runs/37459202051),
commit `a273eba6`, context4096, синтетический русский вход **3072 символа**,
limit128, тот же GGUF и thinking off. NPU вернул exitCode0 / complete=true:
**25,3 ток/с generation / 1345,9 prompt**, весь JNI-вызов10,269 с / CPU9,086 с.
Пик PSS **2,65 ГиБ**, RSS2,72 ГиБ, ownSwap≤18,5 МиБ, свободная MemAvailable
не ниже **3,68 ГиБ**. Watchdog не сработал. Это подтверждает размещение модели
и буферов в этой реальной пробе с context4096, но не полный занятый контекст4096,
context8192 или одновременное чтение TTS. Системная память других приложений
между пробами менялась; нельзя считать разницу пиков следствием одного context.

Контроль того же входа3072 / context4096 / limit128 в новых процессах:

| Устройство | Весь запрос с загрузкой | CPU time | Prompt ток/с | Generation ток/с | Пик PSS |
|---|---:|---:|---:|---:|---:|
| NPU / HTP0 | **10,269 с** | **9,086 с** | 1345,9 | **25,3** | 2,65 ГиБ |
| CPU2 | 34,473 с | 69,979 с | 44,5 | 13,3 | 3,44 ГиБ |
| OpenCL GPU | 28,367 с | 17,140 с | 107,2 | 14,6 | 2,68 ГиБ |

Все три exitCode0 / complete=true, реальные русские ответы; текст и его
семантическая пригодность для TTS здесь не оптимизировались. NPU в этой пробе
быстрее CPU2 по всему вызову **в 3,36 раза**, расход CPU time **на 87,0% меньше**.
Относительно OpenCL GPU полный вызов быстрее в2,76 раза, CPU time ниже на47,0%.
Это одинаковый пакет/runtime/вход/лимит, но короткий одиночный запрос для каждого
устройства, без контроля thermal state; ответы между устройствами различаются.
MinMemAvailable CPU2 3,51 ГиБ, GPU2,94 ГиБ. GPU allocations выросли глобально
примерно на1,88 ГиБ, не складывать с PSS. Батарея этими данными не измерена.

## Энергия и интеграция

Заряд, ток батареи и ватты не измерялись, по прямому указанию пользователя.
Снижение CPU time и длительности относительно CPU2 даёт разумное основание
ожидать экономию при переносе **CPU → NPU**. NPU и RAM тоже расходуют энергию;
процент экономии и выигрыш перед LiteRT GPU этими метриками не установлен.

Для экспериментальной интеграции предпочтителен **Q4 GGUF + ggml-hexagon**:
маленький файл, обычный app UID, меньше CPU time, нет второй версии QNN для Gemma.
Нужен persistent JNI-адаптер к прямому llama API с выбором HTP0, thread-safe
очередью и отменой, bounded context, RAM admission и выгрузкой. Библиотеки
V79/V81 и их ABI закреплять вместе; проверить упаковку C++ runtime с текущим
приложением. Доступ FastRPC доказан в обычном пробнике, но работу внутри MyTTS
и одновременное непрерывное LLM + TTS пока не проверяли.

Точка подключения в нашем базовом дереве — `LlmProviders.local()`:
там уже находятся последовательная обработка, общий deadline/cancel generation,
`LocalSpeechText.response` / валидация ролей и idle unload. Заменять нужно только
реализацию local engine, сохранив эти механизмы. Для NPU отдельные GGUF download
manifest/проверка SHA и backend setting; GPU LiteRT оставить доступным. Ввести
token-aware admission: вход + output budget + шаблон должны помещаться в bounded
context. Сейчас LiteRT настраивает8192, поэтому короткая проба512 не подтверждает
поддержку полного рабочего лимита. Ошибку NPU явно фиксировать и возвращаться
к существующему резерву, не выдавать CPU fallback за NPU. Контрольные timings
в production должны включать prefill/decode и реальный completed output.

Наш мост к benchmark/CLI — диагностический прототип. Он меняет stdout, signal
handlers и process-wide registry; переносить его как production provider нельзя.
Native CLI `0ef6e55` требует локальный HTTP socket даже при `-m local.gguf`:
первый APK без INTERNET упал до загрузки (`failed to get a free port`), этот
запуск исключён. В исправленном APK разрешён INTERNET как необходимая
Android permission для loopback; аргументы remote server/model URL не передаются.
Прямой llama API устранит этот внутренний CLI-сервер.

Raw результаты и анализ: `docs/gemma4-npu/2026-10-06-hexagon-app-*`.
Предварительные root-cli измерения сохранены отдельно, не смешивать с app UID.

## Состояние после проверки

Пробник force-stopped, процессов probe/llama-cli/llama-bench нет. Открыт MyTTS,
его APK/настройки озвучки не менялись. USB stay_on восстановлен0 и проверен,
текущий screen_off_timeout15000 не изменялся этим агентом, громкость не трогалась.
Это завершённая проверка второго runtime и диагностический прототип в отдельной
ветке; production NPU-provider MyTTS ещё не подключён и слияние не выполнялось.
